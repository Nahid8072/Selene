# 07 — Benchmark Protocol

## Objective

Measure whether AgentScale reduces repeated upstream Git data transfer and workspace preparation cost for concurrent jobs. The benchmark must be repeatable, fair and honest about trade-offs.

## Experimental configurations

Use at least these configurations:

- **A — Standard Git:** each worker independently clones the same pinned repository revision and checks out the same declared scope.
- **B — Optimized Git baseline:** use relevant native Git features such as partial clone (`--filter=blob:none`) and sparse checkout where the origin supports them. The configuration must be documented and must produce the same required workspace contents.
- **C — AgentScale:** one node-local bare mirror/cache is populated once; each workspace is provisioned as a private clone using the shared cache object database through Git alternates.

Do not compare a full standard clone against an AgentScale sparse checkout and call the result an apples-to-apples win. Either use identical materialized paths for all modes or report separate full-checkout and sparse-checkout experiments.

## Datasets

Use two types:

1. **Real public repositories** for external validity. Start with practical sizes such as React and Kubernetes; pin exact commit SHAs. A much larger repository such as Linux can be an optional stress dataset if hardware and disk allow.
2. **Synthetic deterministic repository** generated by a script, with configurable file count, file size, history depth, binary/text ratio and shared-path overlap. This lets the team vary the workload without relying on a remote repository changing.

Never benchmark against a moving branch without recording the resolved commit SHA.

## Workload dimensions

- Concurrency: 1, 5, 10, 25, 50 (100 only if machine capacity permits).
- Cache state: cold and warm.
- Repository: each pinned dataset.
- Workspace scope: full checkout and, in a separate scenario, selected sparse paths.
- Repetitions: at least 5 for development; target 10 or more for final report where runtime allows.
- Seed: fixed and recorded for synthetic scenarios.

## Cold vs warm semantics

- **Cold AgentScale trial:** begin with no local mirror/cache for the repository. Measure upstream fetch/population time and bytes separately from the subsequent batch of workspace provisioning. Report both total batch cost and per-workspace cost.
- **Warm AgentScale trial:** cache mirror already contains the pinned revision. Measure workspace provisioning and any additional upstream transfer.
- **Baseline:** ensure each trial begins with a clean workspace directory. Distinguish OS page-cache effects where possible; do not label a run “cold” merely because the application cache directory is empty if the host page cache remains warm.

## Metrics

Primary:
- Workspace provisioning latency: median, p95 and p99 where sample count supports it.
- Upstream network bytes sent by origin.
- Successful workspaces per second.
- Failure rate.

Secondary:
- CPU usage.
- Peak/average memory.
- Disk read/write bytes.
- Cache hit/miss count (AgentScale only; not applicable to plain baseline).
- Cache disk footprint.
- Warm-up cost and amortized cost per workspace.

Use Docker container network I/O counters where the origin runs in an isolated container. Docker documents network I/O and block I/O in container stats. If bytes cannot be measured reliably on the chosen platform, mark the field unavailable; do not fabricate it.

## Fairness controls

- Same host, CPU and memory limits.
- Same repository commit SHA.
- Same materialized file set.
- Same number of successful workspaces.
- Same concurrency schedule.
- Same network conditions.
- Same timeout and retry policy.
- Repeat each mode in alternating/randomized order where practical to reduce order bias.
- Record Git version, OS/kernel, Docker version, CPU, RAM, storage type and network setup.
- Report failed trials instead of silently discarding them.

## Data outputs

For every run, save:

- `config.json`: dataset, commit, mode, concurrency, seed, cache state and environment.
- `workers.jsonl`: one record per worker with start/end time, status and error code.
- `metrics.json`: host/container measurements and data source.
- `summary.json`: aggregate statistics.
- `README.md`: exact command and how to reproduce.

Keep raw data immutable. Generate charts from raw data; do not manually edit result values.

## Required final charts

1. Provisioning latency vs concurrency.
2. Upstream bytes vs concurrency.
3. Successful workspaces/second vs concurrency.
4. CPU and peak memory vs concurrency.
5. Cold-cache total cost vs warm-cache batch cost.
6. Failure rate and correctness test results.

## Interpretation rules

- A warm-cache win does not prove cold-cache improvement.
- A local mirror is likely to help repeated access to the same repository; do not generalize to one-off jobs or unrelated repositories.
- A reduction in upstream bytes may trade off local disk space or initial warm-up cost.
- Report absolute values and relative changes, with units and trial counts.
- Never use Anthropic's Scion performance claims as AgentScale targets or results.
